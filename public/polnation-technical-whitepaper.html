1. Abstract

Polnation is a non-custodial soft staking platform deployed on the Polygon Proof-of-Stake (PoS) network. The protocol enables USDC holders to earn daily yield without transferring tokens, granting approvals, or interacting with any smart contract that could move their funds.

This technical whitepaper provides a deep dive into four critical areas:

  • Zero-Approval Security Model — How user funds remain completely untouched and how users can independently verify this
  • Merkle Tree Distribution — The cryptographic mechanism used for trustless, gas-efficient reward claims
  • Revenue Architecture — Where yield originates, with on-chain verifiable proof for each revenue stream
  • Compliance Framework — Regulatory considerations and risk disclosure

Core Guarantee: At no point does Polnation have the ability to access, transfer, lock, or freeze any user's USDC. This is not a policy — it is an architectural impossibility enforced by the absence of any on-chain token approval.

2. System Architecture

The Polnation system consists of three independent layers that interact through well-defined interfaces:

Figure 1 — Three-layer architecture: User Layer → Computation Layer → Blockchain Layer

Key Design Principles

  • Separation of concerns: The computation layer NEVER holds private keys to user wallets. It only reads public on-chain data and publishes Merkle Roots.
  • Trustless verification: Every output of Layer 2 (Merkle Root) is verifiable on Layer 3 by any independent observer.
  • No single point of custody: User funds exist solely on the USDC contract. Polnation has no contract that can custody, lock, or transfer user tokens.

3. Non-Custodial & Zero-Approval Model

The most critical security property of Polnation is its zero-approval architecture. Understanding what this means requires knowledge of how ERC-20 token approvals work — and why Polnation deliberately avoids them.

3.1 What Are Token Approvals?

In the ERC-20 standard, approve(spender, amount) grants a third-party contract permission to call transferFrom() on your tokens. This is how DEXes (Uniswap), lending protocols (Aave), and bridges move your tokens.

⚠️ The Risk: Any contract with a non-zero approval on your tokens can call transferFrom(owner, recipient, amount) at any time to move your tokens — even without your interaction. Malicious or compromised contracts with approvals can drain wallets. This is the #1 attack vector in DeFi exploits.

5. Merkle Tree Distribution — Deep Dive

Polnation distributes rewards using a Merkle Tree claim model — the same mechanism behind Uniswap's $UNI airdrop ($6.4B distributed), Arbitrum's $ARB airdrop ($2.3B), and Optimism's $OP retroactive public goods funding. This section explains the cryptography in detail.

5.1 What is a Merkle Tree?

A Merkle Tree is a binary hash tree where:

  • Leaf nodes contain the hash of raw data: keccak256(abi.encodePacked(address, amount))
  • Internal nodes contain the hash of their two children: keccak256(leftChild + rightChild)
  • Root node (Merkle Root) is a single 32-byte hash that uniquely represents ALL data in the tree
Figure 4 — Merkle Tree structure with Alice's proof path highlighted (yellow dashed = proof nodes). Only 2 hashes needed to verify a claim in a tree of any size.

5.3 Security Properties

  • Collision Resistance: Finding two different datasets that produce the same Merkle Root requires breaking keccak256 — computationally infeasible (~2¹²⁸ operations).
  • Tamper Evidence: Modifying any single leaf (e.g., changing Alice's $12.50 to $12.51) produces a completely different root hash. The on-chain root acts as an immutable commitment.
  • Replay Protection: The contract maintains a claimed[address] mapping. Each address can only claim once per distribution cycle.
  • Double-Claim Prevention: After a successful claim, the contract sets claimed[msg.sender] = true, preventing re-execution of the same proof.

5.4 Pseudocode: Merkle Distributor Contract

contract MerkleDistributor { bytes32 public merkleRoot; mapping(address => bool) public claimed; function claim( uint256 amount, bytes32[] calldata proof ) external { // 1. Prevent double claims require(!claimed[msg.sender], "Already claimed"); // 2. Compute the leaf hash bytes32 leaf = keccak256( abi.encodePacked(msg.sender, amount) ); // 3. Verify Merkle proof require( MerkleProof.verify(proof, merkleRoot, leaf), "Invalid proof" ); // 4. Mark as claimed claimed[msg.sender] = true; // 5. Transfer USDC rewards USDC.transfer(msg.sender, amount); } }

8.2 Risk Disclosures

⚠️ Important Risks:
  • Smart Contract Risk: While the Merkle Distributor follows battle-tested patterns, all smart contracts carry inherent risk
  • Yield Variability: Returns depend on validator performance, ecosystem programs, and platform growth — they are not guaranteed
  • USDC Depegging Risk: USDC is a centralized stablecoin managed by Circle. A depeg event would affect all USDC holders
  • Polygon Network Risk: Network congestion, validator downtime, or consensus failures could delay distributions
  • Regulatory Risk: Changes in cryptocurrency regulations may affect platform operations in certain jurisdictions

8.3 User Protections

  • Worst-case scenario analysis: If Polnation ceases operations tomorrow, users lose $0 — their USDC remains in their own wallet, untouched
  • No approval = no exposure: Unlike DeFi protocols that require token approvals, Polnation has zero on-chain authority over user tokens
  • Transparent distribution: All Merkle Root updates and claim transactions are publicly visible on PolygonScan
  • No withdrawal lock: Users can move their USDC at any time with zero restrictions or penalties

10. Glossary

TermDefinition
Merkle TreeA binary hash tree where each leaf contains a hash of data, and each parent contains the hash of its children. The root hash represents all data.
Merkle RootThe single 32-byte hash at the top of the tree. Stored on-chain as a commitment to all user rewards.
Merkle ProofA compact set of sibling hashes (O(log N)) that allows verification of a specific leaf's inclusion in the tree.
keccak256The cryptographic hash function used by Ethereum and Polygon. Produces a 256-bit (32-byte) hash.
balanceOf()A standard ERC-20 function that returns the token balance of an address. Read-only, requires no authorization.
approve()An ERC-20 function that grants a spender permission to move tokens. Polnation NEVER calls this.
allowance()An ERC-20 function that returns the approved amount for a spender. For Polnation, this always returns 0.
transferFrom()An ERC-20 function to transfer tokens on behalf of an owner. Requires prior approval. Polnation cannot call this.
Non-custodialA design where the platform never holds, controls, or has access to user funds.
Polygon PoSA Layer 2 Proof-of-Stake blockchain built on Ethereum, offering low fees and fast transactions.
CheckpointA periodic snapshot of Polygon block state submitted to Ethereum L1 by validators.
ValidatorA node that participates in block production and consensus on the Polygon network.
stMATIC / MaticXLiquid staking tokens representing staked POL via Lido and Stader protocols, respectively.
