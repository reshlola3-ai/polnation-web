# Dev Log — 2026-04-23

## 主要变更：polygon-clone 主页 FOUC 与「双 logo / 螺旋失踪」修复（第一阶段）

### 背景

主页 `/` 在 [middleware.ts:5-7](../middleware.ts) 里被 rewrite 到一份**静态 HTML**：
[`public/polygon-clone/index.html`](../public/polygon-clone/index.html)（2956 行）。
这份 HTML 是从 polygon.technology 扒下来的 webflow 站，所有 Polnation 化都靠
**底部一段内联 `<script>`** 在 `window.load` 后用 JS 改 DOM 完成（文字替换、logo 注入、
section 重建、链接重映射等）。

这种「先 ship 旧 HTML，再 JS 替换」模式带来三个问题：

1. **FOUC**：首屏先看到 Polygon 旧文案，1-2 秒后才被 JS 改成 Polnation —— 手机端尤其明显
2. **手机双 logo**：上下出现两个 Polnation logo，一闪即逝
3. **螺旋失踪**：六边形 + 螺旋 video（"Powered by $POL" 区块）整段消失

之前曾尝试一次性 bake 全部 JS 改动到 HTML（commit `3cca6d4e`），结果**重叠和螺旋问题
全部暴露**，被回滚（commit `a922c3a0`）。这次改用**增量 bake** 策略，每轮一个小批次
独立验证。

## 4. 双 logo 闪烁修复

**Commit：** `e6e11cb5 fix(navbar): hoist polnation logo display rules to <head>`

### 现象

手机端首次加载时，**Polnation logo 上下出现两个**，一闪即逝。

### 根因（CSS race condition）

[`polygon.css`](../public/polygon-clone/polygon.css)（534KB，head 里 `<link>` 加载）有
一条**全局规则**：

```css
img { display: inline-block !important }
```

我们的 logo 隐藏规则在 [body 末尾的 inline `<style>` 块](../public/polygon-clone/index.html#L1967)：

```css
.polnation-nav-brand .polnation-logo-on-dark { display: none !important; }
.polnation-nav-brand .polnation-logo-on-light { display: block !important; }
@media (max-width: 991px) {
  body:not(.nav-scrolled) .polnation-logo-on-light { display: none !important; }
  body:not(.nav-scrolled) .polnation-logo-on-dark { display: block !important; }
}
```

specificity 我们赢（`(0,2,1)` vs `(0,0,1)`），但**解析时序**：

1. head 解析 → polygon.css 加载 → 全局 `img { display: inline-block !important }` 生效
2. body 解析到 [line 370](../public/polygon-clone/index.html#L370) → 两个 `<img>` tag 渲染
   → **此时只有 polygon.css 在管它们 → 两个都显示**
3. body 解析到 line ~1967 → 我们的隐藏规则才生效 → 隐藏一个

第 2 → 第 3 步之间这个 gap 在桌面端瞬间，在手机端因为 CPU 慢、屏幕上下排版，
**肉眼可见 → "两个 logo 一上一下"**。

### 修复

在 `</head>` 之前插入一个小 `<style>` 块，把 4 条 logo display 规则**提前到 head**：

```html
<style>
.polnation-nav-brand .polnation-logo-on-dark { display: none !important; }
.polnation-nav-brand .polnation-logo-on-light { display: block !important; }
@media (max-width: 991px) {
  body:not(.nav-scrolled) .polnation-nav-brand .polnation-logo-on-light { display: none !important; }
  body:not(.nav-scrolled) .polnation-nav-brand .polnation-logo-on-dark { display: block !important; }
}
</style>
```

head 解析比 body 早 → polygon.css 一起 parse 时就有我们的规则可比 → 高 specificity
赢 → **永远只显示一个**。body 末尾的同样规则保留作冗余安全网。

### 回滚

```bash
git revert e6e11cb5
```

## 7. 视频 404 全面修复（R5 视频路径 done）

**Commit：** `393ae388 fix(videos): bake video src paths to absolute, drop ensureLocalVideoPaths`

### 现象

Chrome DevTools console 报 7 条 `net::ERR_ABORTED 404`：

```
GET https://www.polnation.com/assets/videos/coin-loop.webm        404  ← 螺旋!
GET https://www.polnation.com/assets/videos/oms-loop.webm         404
GET https://www.polnation.com/assets/videos/oms-expand.webm       404
GET https://www.polnation.com/assets/videos/oms-mobile-a-chain.webm   404
GET https://www.polnation.com/assets/videos/oms-mobile-b-trails.webm  404
GET https://www.polnation.com/assets/videos/oms-mobile-c-wallet.webm  404
GET https://www.polnation.com/assets/videos/oms-mobile-d-bpn.webm     404
```

**包括我们刚刚救回来的螺旋 video** —— section 在但 video 是空的。

### 根因

7 个 `<video>` 标签 src 是相对路径 `src="assets/videos/..."`。浏览器解析成
`https://www.polnation.com/assets/videos/...`，但实际文件在
`/polygon-clone/assets/videos/...`。

[index.html:2500](../public/polygon-clone/index.html#L2500) 有个 `ensureLocalVideoPaths()`
本来应该补全路径，但它只在 `initializeHeroVideo()` 里被调用，而 load handler 是：

```js
window.addEventListener('load', function () { ... initializeHeroVideo(); ... });
```

`window.load` **是所有资源加载完后才触发的**。执行顺序：

1. HTML parse → 浏览器立刻请求 `/assets/videos/...` → **404 ❌**
2. 资源全部完成（包括失败的 404）→ ERR_ABORTED
3. `window.load` 触发 → `ensureLocalVideoPaths()` 跑 → 改 src
4. 但浏览器**已经放弃这次请求**，video 元素也不会自动重试

### 修复

R5 视频路径直接 bake：

```bash
# HTML 里 8 处 (7 + 1 已 baked) src 全部写死绝对路径
src="assets/videos/X.webm"  →  src="/polygon-clone/assets/videos/X.webm"
```

同时**删掉 `ensureLocalVideoPaths` 函数 + `initializeHeroVideo` 里对它的调用**
（保留 hero video 的 play 事件回调）。

净 -10 行 JS。

## 8. 待修：导航 logo 白盒（已讨论，未实施）

### 现象

桌面端 + 手机端，导航栏 polnation logo 周围有一个**白色矩形盒子**，比 logo 实际宽度
大很多，往右延伸到菜单 item 之前；和 nav 其他区域颜色不一致，**很丑**。

### 根因（来自 polygon.css 的两条规则叠加）

```css
.nav-brand-wrap {
  background-color: var(--color--interverted-primary);  /* ← 白色 */
  flex: 1;       /* ← 占据剩余所有横向空间 */
  display: flex;
}
```

我们[在 1923-1927 行](../public/polygon-clone/index.html#L1923-L1927) 已经写了
`.nav-brand-wrap { background: transparent !important }` 试图覆盖。但 screenshot 显示
没赢 —— 怀疑跟之前双 logo 同款 race condition：覆盖规则在 body 末尾内联 `<style>` 里，
解析晚于 head 的 polygon.css。

### 备选修复方案（讨论中）

**保险方案（不依赖 DevTools 排查）**：在 head 内联 `<style>` 加：

```css
.nav-brand-wrap {
  background: transparent !important;
  background-color: transparent !important;
  flex: 0 0 auto !important;       /* 不要再霸占整条横向空间 */
}
.nav-bg-layer {
  background-color: transparent !important;
}
body.nav-scrolled .nav-brand-wrap {
  background: transparent !important;
}
```

为什么这样：
- `flex: 0 0 auto` —— 让 brand-wrap 只占 logo 实际宽度
- 三层 background 都 `!important` 全打掉，不知道哪条赢就全覆盖
- 放 head 里跟 logo 修复同一招，规避 race condition

**风险**：改完 logo 可能位置偏左，需要单独再调 padding。

### 关于"统一颜色"的设计取舍

用户问「能不能改成统一颜色统一背景」——可以，但是设计取舍问题：

| 方案 | 优点 | 缺点 |
|---|---|---|
| 永远透明 + 浅色 logo | 干净，零切换闪烁 | 滚到下面白色 section 时菜单看不见 |
| 永远白色 + 深色 logo | 永远清晰可读 | 盖住 hero 视频的视觉冲击力 |
| **保留两态 + 修白盒（推荐）** | 视觉自然过渡 | 切换瞬间需要平滑 |

倾向方案 3：保留两态切换逻辑，只把 `.nav-brand-wrap` 那个流氓白盒干掉。

### 还需要确认

- Live treasury tracker 标题是**深色**而不是白色，看不清。需要给

## 11. 经验沉淀

1. **不要 big-bang bake** webflow 类站点 —— 它们的 CSS / 动画对 DOM 结构和加载时序很
   敏感。一次只动一小块，独立验证再做下一块。
2. **`!important` 不能解决加载时序问题** —— specificity 战争只在所有规则都 parse
   完后才生效。涉及加载阶段视觉稳定性的 critical CSS 必须放在 `<head>` 里，最好
   放在外部 `<link>` 之前。这次双 logo race + 白盒 race 都是同源问题。
3. **视觉 bug 要先排"主动删除"再排 CSS** —— 螺旋失踪那次如果直接去看 CSS / 看
   z-index / 看 display，会绕远路。先 grep `.remove()` 和 `display:none` 是更快的
   定位手段。
4. **commit 粒度要小** —— 这次每个修复一个 commit，一个 commit 一个明确目的，
   出问题 `git revert` 就行，不影响其他工作。
5. **`window.load` 太晚** —— 所有资源加载完才触发，**对于"修复网络请求路径"这类
   工作彻底没用**，因为浏览器已经按原路径请求并失败/abort 了。视频路径修复必须在
   HTML 阶段做，不能 hook `load`。
6. **Polygon eyebrow 的 `margin-bottom: -2.8em` 是个反复出现的噩梦** ——
   `.h-eyebrow-container.is-relative` 这个 class 出现在很多地方（featured / tracker /
   …），每次塞进我们的紧凑容器都要单独 override。可以考虑统一一条更通用的 reset。
7. **Windows 中文系统 + Edit 工具 = 法语乱码** —— 详见第 12 节。永远用 Python 脚本
   写非 ASCII 字符到文件，不要用 Edit 工具直接写法语/中文/其他非 ASCII 内容。

## 12. 首页 i18n 翻译功能（2026-04-25）

### 背景

用户要求给首页加语言切换功能，支持法语翻译。

### 方案选择

| 方案 | 代价 | 风险 |
|---|---|---|
| 集成 next-intl（Next.js i18n） | 大改：首页要变成 Next.js 路由 | 破坏现有 Webflow CSS/动画，等于重写首页 |
| **JS 层翻译（选用）** | 小：inline script 里读 cookie 切语言 | 低，不动 HTML 结构 |

选 JS 层方案：在 `public/polygon-clone/index.html` 现有的第二段 inline `<script>` 里加翻译逻辑。next-intl 已经在浏览器端设置 cookie，直接读取。

### 实现结构

```javascript
// 语言检测：读 next-intl cookie
var POLNATION_LANG = (document.cookie.match(/(?:^|;\s*)NEXT_LOCALE=([^;]+)/) || [])[1] || 'en';

// 翻译表
var FR_REPLACEMENTS = [
  ['English text', 'French text'],
  ...
];

// 遍历 DOM 文本节点，做字符串替换
function applyFrTranslations() { ... }

// Navbar 语言切换按钮
function updateLangButton() {
  // 在 navbar 右侧注入 EN | FR 切换按钮
}

window.addEventListener('load', function() {
  updateLangButton();
  if (POLNATION_LANG === 'fr') {
    applyFrTranslations();
    // 2.5s 延迟二次翻译：fetchAndApplyLiveStats() 异步覆盖文本后再翻一遍
    setTimeout(function() { applyFrTranslations(); }, 2500);
  }
});
```

### 动态文本问题

`fetchAndApplyLiveStats()` 是异步的，API 返回后会用英文覆盖 hero subtitle 和 stats heading。解决方案：load 事件后 2.5s 再跑一次 `applyFrTranslations()`，捕获 API 写入后的文本。代价是这部分文字有 2.5s 的英文→法文延迟。

### Windows GBK 编码 Bug（关键经验）

**现象**：翻译部署后浏览器显示乱码（法语 é 变成 CJK 字符芅）。

**根本原因**：这台 Windows 中文系统的代码页是 CP936（GBK）。Edit 工具在写入非 ASCII 字符时，法语字符（如 `é` = UTF-8: `C3 A9`）被错误编码为 CJK codepoint（`E8 8C 85` = U+8305 芅）。浏览器声明 `charset=utf-8`，读到这些 3 字节序列，显示的是汉字而非法语字母。

**诊断方式**：

```python
with open('index.html', 'rb') as f:
    raw = f.read()
print('c3 byte count:', raw.count(bytes([0xc3])))  # 应该 > 0，如果 = 0 说明没有正确 UTF-8 法语字符
print('e8 byte count:', raw.count(bytes([0xe8])))  # 如果 >> 0 说明有 CJK 污染
```

**修复方式**：用 Python 脚本直接写二进制，绕过系统编码：

```python
correct_text = "Récompenses"  # Python 源文件用 UTF-8 存，\u 转义更安全
correct_bytes = correct_text.encode('utf-8')  # 明确 UTF-8 编码
# 读文件 → 找到对应区段 → 替换字节 → 写回
with open('index.html', 'rb') as f:
    raw = f.read()
new_raw = raw[:start] + correct_bytes + raw[end:]
with open('index.html', 'wb') as f:
    f.write(new_raw)
```

**永久规则**：**今后在这台机器上，所有需要写非 ASCII 字符（法语、中文等）到文件的操作，必须通过 Python 脚本用 `.encode('utf-8')` 写入，不能直接用 Edit 工具。**
